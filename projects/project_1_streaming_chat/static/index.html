Streaming Chat - three patterns, same backend

Same prompt. Same LLM call. Three transport patterns side by side so you can feel the difference.

POLLING Wait, then show whole answer

Client fires a job, then polls /api/polling/status/<id> every second until status is done, then fetches the full result. UX: blank → spinner → BLAM, the whole answer.

status: idle polls fired: 0 first byte: - total: -

SSE Tokens stream in over HTTP

Client POSTs to /api/sse/chat and reads the body as an SSE stream of event: token messages. UX: words appear as they're generated.

status: idle tokens: 0 first byte: - total: -

WS Streamed + interruptible

Persistent WebSocket. Same streaming UX as SSE, plus client can interrupt the LLM mid-response (try clicking Interrupt during a long answer).

conn: disconnected status: idle tokens: 0 first byte: - total: -
What to watch:
  1. Polling spends ~N requests doing nothing, then dumps the whole answer.
  2. SSE feels instant - first token in <1s, words pour in.
  3. WebSocket feels identical to SSE for output, but you can interrupt mid-stream. That's the bidirectional advantage.
